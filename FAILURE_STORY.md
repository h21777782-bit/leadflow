# Failure Story — Simulated HighLevel Outage, Retry, Recovery

> **This is a demo scenario, run on my own machine with fictional data — not a real client
> incident, not a real HighLevel account, and not a real outage.** Every "HighLevel" response
> below is generated by this project's own mock provider (`MOCK_MODE=true`, the default), and is
> printed with a `[SIMULATED]` label everywhere it appears in the UI and in these logs. Describe
> it in an interview exactly that way: *"here's a failure scenario I can reproduce on demand to
> show how the retry and recovery machinery actually behaves."*

## What this demonstrates

A lead is created → LeadFlow tries to sync it to HighLevel → HighLevel (simulated) is down with a
503 → the job fails and schedules a retry with backoff, visible in the UI and the database, not
swallowed → the simulated outage ends → the worker's normal retry schedule picks the job back up
on its own, with no manual intervention → the contact is confirmed synced → every attempt, every
HighLevel call, and every audit event is inspectable afterward.

The point isn't "look, an error happened" — it's that the *system* correctly classified the
failure as transient, recorded it without losing data, retried it automatically, and left a
complete, honest trail of exactly what happened and when.

## How to reproduce this exact run

```bash
npm run db:seed      # start from a known-clean state — see DEMO_COMMANDS.md §15 for why this matters
npm run demo:crm
```

The script (`scripts/demo-crm.ts`) is idempotent and safe to run repeatedly — it removes leads
from any earlier `demo:crm` run before starting. It runs entirely through the same services and
worker code the real app uses (`createContact`, `runOnce`, the real `crm.sync_contact` job
handler) — nothing about the retry/recovery logic below is special-cased for the demo.

## Walking through it live (talking points)

1. **`/integrations`** → point at the failure switch (off/transient/503/timeout/401) and the
   **Recent integration calls** table — this is real data from the `integration_calls` table, not
   a hardcoded UI mock.
2. Flip the switch to **503**, then either run `npm run demo:crm` again or create a lead in the
   UI and watch its sync job fail with the exact simulated error, shown with a retry time — not a
   silent failure, not a raw stack trace.
3. Flip the switch back to **off**. Either wait for the worker's own backoff schedule, or click
   **Retry Now** on `/failed-automations` — the job completes, and the contact's
   `ghl_contact_id` is now set.
4. Open that contact's page → the activity log shows the failed attempt *and* the successful
   retry, in order, with real timestamps — the same `audit_logs` rows the `/demo` page (Phase 8)
   also renders.

## What's real here versus what's simulated (stated plainly)

| Real | Simulated |
|---|---|
| The job queue, worker, retry/backoff logic, idempotency, and audit trail | The HighLevel API itself — no network call ever leaves the machine in `MOCK_MODE=true` (the default) |
| The Postgres transactions, row locks, and `SKIP LOCKED` claiming | The specific error (`503 Service Unavailable`) — chosen by the demo failure switch, not by an actual outage |
| The classification of a 503 as transient vs. e.g. a malformed-request 400 as permanent (`src/lib/job-errors.ts`) | The lead itself — a fictional contact tagged `demo-automation`, `.example` email domain |

The retry/backoff/idempotency machinery demonstrated here is **exactly** the code path a real
HighLevel outage would exercise — that part isn't a simplified stand-in. What's simulated is
narrowly the HTTP response itself, via the mock provider's fault-injection switch
(`src/server/integrations/crm/mock-provider.ts`), so the failure can be triggered on demand
without needing HighLevel to actually be down.
